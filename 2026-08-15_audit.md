## 3. Pending work — ranked

### 3.1 P0 — Production correctness

#### P0-1 — The body store is unreachable by configuration (TESTED)

`MESSAGE_BODIES=1` was set on prod and `go-api` restarted. The container confirmed
`MESSAGE_BODIES=1`, and the code then **refused to honour it**:

```
[retention] MESSAGE_BODIES=1 REFUSED: the body store caps retention at 3h0m0s
(schema CHECK message_bodies_ttl_cap), but normal messages must be retained for
at least 30 days. Bodies stay on messages.content, which is not reclaimed.
See jobs.MinRetentionDays and bodyStoreRefused().
```

This is not a misconfiguration. It is an **unresolved design conflict**, and the
refusal is deliberate — `bodyStoreRefused()` degrades instead of failing, on the
reasoning that "refusing to boot would turn an operator's mistake into an outage;
refusing to shorten retention turns it into a log line."

The conflict is arithmetic and has no configuration escape:

| Constraint | Value | Where |
|---|---|---|
| Body store TTL ceiling | **3 h** | `message_bodies_ttl_cap` CHECK, [099_message_bodies.sql:111](vaultchat-backend/migrations/099_message_bodies.sql#L111) |
| `bodyTTL()` return | **≤ 3 h always** — `MESSAGE_BODY_TTL_SECONDS` is only honoured when *below* 3 h | [partitions.go:420](vaultchat-backend-go/internal/jobs/partitions.go#L420) |
| Retention floor | **30 days** | `MinRetentionDays`, [jobs.go:72](vaultchat-backend-go/internal/jobs/jobs.go#L72) |
| Gate | `bodyTTL() < 30 days` → refuse | [partitions.go:87](vaultchat-backend-go/internal/jobs/partitions.go#L87) |

`RETENTION_MIN_DAYS` can only raise the floor, never lower it. So `BodyStoreEnabled()`
returns `false` for **every** possible configuration of the current code and schema.

**The redesign the code itself specifies** (comment at [partitions.go:75](vaultchat-backend-go/internal/jobs/partitions.go#L75)):

| # | Work | Effort |
|---|---|---|
| a | Relax the `message_bodies_ttl_cap` CHECK to the retention floor | 0.5 d |
| b | **Per-message TTL** so explicitly-ephemeral messages keep a short life while normal messages honour the 30-day floor | 4 d |
| c | Size the partition window for the floor — **720 hourly partitions at 30 days**, against the 48 the maintenance job keeps today | 2 d |
| d | Migration + backfill + contract test | 2 d |

**Total ~8.5 d.** Until then the 3-hour guarantee is marketing, not behaviour.

## 6. Things worth remembering

1. **Compare prod against `hetzner-deploy`, never against your checkout.** Your working branch legitimately lacks 7 commits that are live.
2. **Normalise line endings before hashing.** The local checkout is CRLF; a raw `md5sum` comparison reports 100% drift that does not exist.
3. **Applied migrations ≠ active feature.** Migration 099 shipped and partitions exist, yet the feature is off. Ledger version is not proof of behaviour — query the data.
4. **An unset flag is not automatically an oversight.** This audit's first draft read `MESSAGE_BODIES` being unset as someone forgetting to set it, and recommended setting it. Setting it proved the opposite: the code refuses it, and the refusal encodes a real unsolved conflict between a 3-hour body TTL and a 30-day retention floor. **Reading the gate before recommending the flag would have caught it** — the config was the symptom, not the cause.
5. **Check the log line, not just the variable.** `printenv MESSAGE_BODIES` returns `1` on prod right now and means nothing. `BodyStoreEnabled()` is the truth, and it says so in the boot log.
