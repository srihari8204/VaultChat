CrazzyChat Microservices

The Go backend split by feature. Go Live, Family Space, Games, Maps, ShopBook and Calls each become their own service around one core, which keeps accounts, chat and the phone's live connection. The boundaries come from the code. The split happens one service at a time after launch, and the app never needs a new release for it.

Seven services behind one front door

The app keeps talking to api.corefinite.com. Caddy looks at each request's path and sends it to the service that owns it. Feature services call core over the private network for three things: live events to phones, push notifications and user names.

What each service owns

Each service owns its paths, its tables and its background jobs. No other service writes to its tables.

Rules every service follows

They keep the phone's experience the same and stop a bug in one service from reaching another service's data.

One front door

The app keeps calling https://api.corefinite.com with the same paths. Caddy sends each path to its service, with core as the fallback. No app release and no new domains.

One live connection

The phone keeps one CC-Wire socket, held by core. Services send live events through core's POST /internal/emit, which already exists; emitx uses it whenever the socket hub runs in another process.

Core signs logins, services check them

Access tokens move from the shared HS256 JWT_SECRET to an Ed25519 key pair, the way the games launch token already works. Core keeps the private key; services get only the public key. Core accepts old tokens for their 15-minute life, then stops.

Secrets stay in core

VAULTCHAT_MASTER_KEY, the lookup pepper and the FCM, MSG91 and Resend keys never leave core. Names are stored encrypted, so services ask core for user names and send notifications through it.

Own tables, own login

One Postgres cluster, one database login per service, with rights only on that service's tables. To change another service's data, call that service.

Read membership live, never copy it

Membership and group permissions are read-only views that core owns. Removing someone from a family takes effect on their next request, in every service.

Account deletion still reaches everything

Service tables keep their foreign keys to users(id) with ON DELETE CASCADE, so deleting an account in core still clears them. The few direct deletes in user.go, such as family_relations, move behind an internal call to the owning service.

Every job runs once

Each background job takes a Postgres advisory lock, so a second copy of a service never runs it twice. For ShopBook this is launch change C2.

/internal stays private

Caddy already refuses /internal/* from the internet. Each service gets its own internal key and listens only on the private network.

Same basics everywhere

/health for Caddy's checks, /metrics for Prometheus, and logs that carry a request ID set by Caddy, so one request can be followed across services.

Family Space without copying membership

A Family Space is a group chat with more features, and every Family Space request checks that chat's membership. If the service kept its own copy of who belongs to a family, someone who was removed would keep seeing live locations until the copy caught up. So the service reads membership from core's live view, and the live-location relay stays in core's socket gateway, which already checks membership on every update.

Moves into Family Space tables

  • From chat_members: location_sharing_enabled, location_sharing_changed_at, role_key, duty_state
  • From chats: shift_start, shift_end, shift_grace_minutes, run_delay_threshold_minutes, leave_allowance
  • Outside Family Space, only groups.go (3 places) and chats.go (1) read them

Stays in core

  • Group membership, invitations and roles
  • Live location and trip updates over the socket
  • spaceName and chatsAudienceAllowed, which sit in Family Space files today but serve chat

The membership view

Core owns it; Family Space and Calls only read it

CREATE VIEW chat_membership AS
  SELECT chat_id, user_id, role, joined_at
    FROM chat_members
   WHERE left_at IS NULL;

GRANT SELECT ON chat_membership TO svc_family, svc_calls;

Test before switching traffic. Remove a member from a test family, then, as that member, call every Family Space route and send a live-location update. Every one must be refused.

Network changes on top of the launch plan

  • fw-core: allow TCP 6432 (PgBouncer) from LIVE-1, 10.20.0.31, so Go Live reaches the database.
  • fw-live: allow TCP 4100 from CORE-1, 10.20.0.11, so Caddy reaches the Go Live service.
  • Core's private listener on 10.20.0.11:8097 also serves /internal/emit, /internal/notify and /internal/users/cards, to LIVE-1 only.
  • Go Live's LiveKit webhooks stay on LIVE-1, so CORE-1 stops receiving them.
  • When CORE-1 runs short, move Maps (Valhalla needs the most memory) and then ShopBook to their own servers. Any service can also run a second copy behind Caddy.

The order to split

Launch first on the tested single API. Then prepare the codebase and move one feature at a time. Each move can be undone by pointing its paths back at core.

  1. Launch on one Go API

    now

    Go live on the four-server plan as it stands. Nothing on this page blocks the launch.

    Done when the two-phone smoke test passes and a week of normal traffic has run.

  2. Prepare the codebase

    estimate: 1 to 2 weeks
    1. Move shared helpers out of feature files. Database helpers (chatsQRow, chatsQueryU, chatsExecU) and text helpers (chatsStrOr, truncRunes, orEmpty) go to shared packages; spaceName and chatsAudienceAllowed go to chat.
    2. Add a SERVICES setting to cmd/api/main.go. SERVICES=all, the default, keeps today's behaviour. SERVICES=golive starts only Go Live's routes and jobs and sends live events to core.
    3. Lock every background job with a Postgres advisory lock (C2).
    4. Sign access tokens with Ed25519.
    5. Add core's internal endpoints for notifications and user names, with one internal key per service.
    6. Create one database login per service, built like vaultchat_sys in migration 133, with rights on its own tables only, and add the membership view.

    Done when no feature file calls another feature's code, and one image starts as core or as any single feature.

  3. Move features out, one at a time

    estimate: 2 to 5 days each; 1 to 2 weeks for Family Space and Calls
    1. Maps, the pilot. It sets the pattern: container, Caddy route with fallback, metrics.
    2. Go Live, onto LIVE-1. Needs Ed25519 tokens first, because it runs on another server.
    3. Games.
    4. ShopBook. Needs the job locks.
    5. Family Space. Needs the column move, the membership view and the removal test.
    6. Calls, last. Ringing stays in core's socket gateway; tokens, call records and history move.

    Done when, for each service, a week passes with normal errors and latency on its own container. Then remove it from core's SERVICES list.

  4. Split the code when a feature earns it

    Give a feature its own binary, database schema, migrations and release version when it gets its own developer, its own release pace or its own load. Until then, one repository with separate containers already gives independent deploys, scaling and failure isolation.

Not included

  • Chat's own parts stay in core. Stories, channels, communities, invitations and chat codes are chat.
  • No second socket on the phone. Every live event still arrives on the one CC-Wire connection.
  • No separate database servers at launch. One Postgres cluster with a login per service is enough until one service's load hurts the others.
  • No message broker. Live events already fan out through /internal/emit and Redis; vaultchat-backend-go/SCALEOUT.md describes when a log-based fan-out would pay off.
  • No Kubernetes requirement. Docker Compose on each server keeps working; the k8s/ folder can come later.
  • No app release and no domain change.
