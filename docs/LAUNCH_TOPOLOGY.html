Server counts here are planning math. The Go backend that serves all traffic has never been load-tested: every results table in docs/PERF_BASELINE.md is empty. The figures come from the Node benchmark it replaced and the repo's LiveKit notes.

Before launch, run scripts/bench/run.sh on a machine with CORE-1's spec and put the measured numbers into the calculator's planning figures.

Choose a region near your users. The repo points at India: routing uses india-latest.osm.pbf, Photon defaults to REGION=in, SMS goes through MSG91, and nginx/sites/vaultchat.conf measured a cold request from India at about 640 ms, 600 ms of it three round trips to Germany. A Mumbai region removes most of that. The topology is the same anywhere.

Keep the hostnames. The app has https://api.corefinite.com compiled in (constants/server.ts). With the same names, moving servers is a DNS change and needs no app release.

Where it runs

Phones reach CORE-1 on 443 for everything except live media, which goes straight to MEDIA-1 and LIVE-1 over UDP. The servers talk to each other only on the private network.

Bring-up order

The order matters: each step needs the one before it. It follows deploy/README.md, adjusted for four servers.

  1. Provision

    all four

    Four servers in one region with a private network between them. Suggested addresses: CORE-1 10.20.0.11, DB-2 10.20.0.12, MEDIA-1 10.20.0.21, LIVE-1 10.20.0.31. Avoid 172.16.0.0/12, which Docker uses.

  2. Prepare each host

    all four
    curl -fsSL https://get.docker.com | sh
docker compose version        # must print v2.x
sudo apt-get install -y fail2ban unattended-upgrades
# CORE-1 only
sudo apt-get install -y nginx certbot python3-certbot-nginx rsync git
# MEDIA-1 and LIVE-1 only: UDP buffers for RTP
printf 'net.core.rmem_max=5000000\nnet.core.wmem_max=5000000\n' | sudo tee /etc/sysctl.d/99-vaultchat-media.conf
sudo sysctl --system

    Then the firewall from the port table. scripts/ops/server-hardening-2026-08-10.sh shows the DOCKER-USER rule shape and runs dry by default; it hardcodes the old box's interface and paths, so adapt it.

  3. Check out and configure

    CORE-1
    git clone -b hetzner-deploy https://github.com/srihari8204/VaultChat.git ~/vaultchat && cd ~/vaultchat
cp deploy/docker-compose.box.yml.example docker-compose.box.yml && chmod 600 docker-compose.box.yml

    Apply changes S1, S2, S4, S5 and S7 from Config changes before the first start. The clone directory must be named vaultchat so container names match the repo's scripts.

  4. Database first

    CORE-1
    dc up -d postgres pgbouncer redis
docker exec vaultchat-postgres-1 pg_isready -U vaultchat

  5. Schema before any API binary

    CORE-1

    A new binary against an old schema fails every request that touches a new column; the reverse is safe. On a fresh database run the ledger loop from deploy/README.md §3.2. When migrating, restore the dump instead and confirm the highest schema_migrations version matches the old box.

    docker exec vaultchat-postgres-1 psql -U vaultchat -d vaultchat -c \
  "CREATE TABLE IF NOT EXISTS schema_migrations (version TEXT PRIMARY KEY, filename TEXT NOT NULL,
   checksum TEXT NOT NULL, applied_at TIMESTAMPTZ NOT NULL DEFAULT NOW())"
cd vaultchat-backend/migrations
for f in $(ls *.sql | sort); do
  v=${f%%_*}; cs=$(sed 's/\r$//' "$f" | sha256sum | cut -c1-16)
  { sed 's/\r$//' "$f"
    printf "INSERT INTO schema_migrations(version,filename,checksum) VALUES ('%s','%s','%s');\n" "$v" "$f" "$cs"
  } | docker exec -i vaultchat-postgres-1 psql -U vaultchat -d vaultchat -v ON_ERROR_STOP=1 -1
done

  6. Start the standby

    DB-2

    Publish Postgres on CORE-1's private address only (S8), create a replication role and allow DB-2 in pg_hba.conf. Run the standby from the same postgres:16 image as CORE-1: a physical replica needs the same major version and the same glibc collation behaviour, which a distro package on a different OS does not guarantee.

    # CORE-1
docker exec -it vaultchat-postgres-1 psql -U vaultchat -c \
  "CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '<strong password>'"
# pg_hba.conf:  host  replication  replicator  10.20.0.12/32  scram-sha-256   (then reload)
# DB-2
docker volume create pgstandby
docker run --rm -it -v pgstandby:/var/lib/postgresql/data postgres:16 \
  pg_basebackup -h 10.20.0.11 -U replicator -D /var/lib/postgresql/data -R -X stream -P
docker run -d --name pg-standby --restart unless-stopped -v pgstandby:/var/lib/postgresql/data postgres:16
# CORE-1: DB-2 should appear as streaming
docker exec vaultchat-postgres-1 psql -U vaultchat -c "SELECT client_addr, state FROM pg_stat_replication"

Network, TLS and media

UFW does not protect Docker ports

Docker's DNAT runs before UFW. Published ports need DOCKER-USER drops matched on --ctorigdstport; a plain --dport match does nothing.

Otherwise Docker creates directories at the mount paths. A root-owned 640 key is also unreadable to coturn's user. Either way there is no TLS listener.

Moving off the current box

For moving from 65.21.229.167 rather than starting empty. The hostnames stay, so users notice a short maintenance window and nothing else.

  1. Copy what cannot be recreated

    Both env files, docker-compose.box.yml, secrets/, .offsite-key, /root/rls-role-passwords.txt, /etc/letsencrypt, the deployed LiveKit YAMLs with real keys, /var/www/admin.corefinite.com, the Valhalla tiles, Grafana's volume if dashboards were made by hand, and /opt/vaultgames with its image if games stay.

  2. Confirm backups upload again

    The off-site copy was failing from 6 September on a revoked R2 token. Take a fresh dump by hand and copy it off the box before touching anything.

  3. Build the new servers alongside

    Bring-up steps 1–14 with the restored data. Test with curl --resolve api.corefinite.com:443:<CORE-1 IP>; device tests need a build pointed at a staging hostname in constants/server.ts.

  4. Lower DNS TTLs

    Set api, stream, admin and turn to 60 seconds a day ahead.

  5. Maintenance window

    Stop go-api on the old box. Take final dumps of vaultchat (and vaultgames if kept), restore them on CORE-1, compare the migration ledger and row counts, then re-seed DB-2.

  6. Move objects

    MinIO holds broadcast segments (5.8 GB) and some legacy media (521 MB on 13 September). Mirror both to R2, or accept losing old broadcast replays.

  7. Switch DNS

    api, stream and admin to CORE-1; turn to MEDIA-1; update the origin for the proxied names in Cloudflare.

  8. Verify

    The checks in bring-up step 13, /build equal to the fingerprint of the tree you deployed, and the two-phone smoke test.

  9. Keep the old box, then wipe it

    Leave it intact and stopped for 14 days as a rollback. When you wipe it, destroy the three loose env backups in /home/srihari that hold live credentials.
