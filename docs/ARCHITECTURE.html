VaultChat System Map

A security-first encrypted messenger that grew a mini-app platform. One Expo/React Native client, one Go service behind Caddy on a single Hetzner box, one Postgres. Everything below was read out of the tree — route registrations, compose profiles, migration files, flag defaults — not from the older prose docs, two of which are stale.

Production topology

vaultchatprod01 · 65.21.229.167 · api.corefinite.com

Four hops from the phone to the process. The two reverse proxies are not redundancy: host nginx owns 80/443 and terminates Let's Encrypt, so Caddy binds a loopback port and acts as the per-route switch — the place a single route can be flipped back to the legacy Node build without touching TLS.

Realtime

One hub, ~60 event names. Rooms are per-chat, per-user, per-call, plus an admin firehose that carries metadata only — event, chat, type, timestamp, never content.

  • Messaging — join_chat, new_message, message_delivered, message_read, typing_start/stop, reaction_updated, resync
  • Calls — incoming_call, join_call, call_roster, call_peer_joined/left, call_media_key, call_mesh_full, screen_share_start/stop
  • VaultBeam — vaultbeam_offer/answer/ice/have/pull/ready/tier/end (a full transfer protocol over the socket)
  • Spaces — run_subscribe, run_update, run_end, trip_update, live_location_update
  • Broadcast — viewer_joined, viewer_activity, channel_join/leave

Cross-node correctness lives in Redis, not in process memory: vc:pres:<uid> hashes count sockets per node, vc:node:hb:<node> heartbeats expire, and a dead node's users stop counting as online before the janitor even runs. That matters because presence gates call wake-push suppression — a stale “online” means a silent missed call.

Background jobs

All in-process goroutines on tickers, each kicked once at boot so a restart-happy container still sweeps.

  • sweep-expired-messages · sweep-expired-chats (code chats with a 1h/3h life)
  • media-retention · sweep-expired-stories · broadcast-retention
  • delete-on-delivery + its body-store twin, both under one flag
  • expire-bodies — the hard 3-hour ceiling, deliberately not gated on that flag
  • scheduled-messages · partition maintenance · ShopBook jobs
  • broadcast-reaper — frees a host wedged by an egress that died without a terminal webhook
  • golive-host-sweep — 90-second disconnect grace, safe only because host_left_at exists
  • vaultbeam sweep — hourly, plus one immediate run at startup

The server is not the source of truth for history. With delete-on-delivery on, getMessages() alone loses the past — any surface that reads history has to union with localDb. Gallery and contact-info already do; chat export is the remaining exposure.

Why ciphertext lives in a second table

Migration 099 split the message body out of messages rather than partitioning messages itself. Three constraints forced it, and the reasoning is worth keeping visible because it looks like duplication otherwise:

1 · six foreign keysPartitioning would force messages_pkey to become (id, created_at) and drag four other tables into composite FKs.
2 · partial unique indexesUnsupported on partitioned tables — and ux_messages_client_dedup is the send-idempotency guarantee. Partitioning would delete it.
3 · DROP PARTITION skips FK actionsThe CASCADEs on bookmarks and poll votes would be silently bypassed by the exact mechanism retention relies on.

message_bodies has no inbound foreign keys — which is precisely what makes DROP PARTITION legal — and is partitioned hourly. That is a security improvement, not just a schema one: UPDATE … SET content = NULL leaves the old heap tuple, ciphertext and all, until autovacuum arrives. Dropping a partition removes the bytes.

06

Crypto & flags

constants/flags.ts is the source of truth

What protects what

  • 1:1 messages — X3DH + Double Ratchet, @noble/curves · hashes · ciphers, the same code running under Node and Hermes with shared test vectors.
  • Groups — Signal-style sender keys distributed over the pairwise ratchet.
  • Media — per-file AES-256-GCM; the key rides the encrypted message, the bytes ride S3.
  • Stories — per-viewer wrapped content key, so the audience list is enforced by cryptography and not only by a query.
  • Live location — its own crypto path (liveLocationCrypto), shared by Spaces and family maps.
  • Calls — callCrypto media keys exchanged over the socket; media itself never touches go-api.
  • Server-side PII — envelope-encrypted through internal/vault; contact sync only ever sees peppered phone hashes.
  • Broadcast — not E2EE and the one mode that says so on screen before you publish.

Boot-time refusals

Two guards that turn silent catastrophes into loud ones:

  • JWT_SECRET empty → refuse to start. An unset value would verify forged tokens against every authenticated route while presenting as a healthy deploy. Under 32 chars is a warning, not a fatal — a length rule would turn hardening into an outage for a short-but-real production secret.
  • /ready returns 503 when Postgres is unreachable, 200 when only Redis is. Redis loss degrades (in-process rate limiting, local socket maps); Postgres loss is an outage. /health always answers 200 so an orchestrator never restart-loops through a database problem.

07

Where this bites

failure modes with a history

Migration 127 is pending

auth.go and user.go name refresh_tokens.token_lookup and revoked_reason in plain SQL — no flag, no capability probe. A go-api built from current main against a pre-127 schema answers every sign-in, refresh and session-list with 42P01: a total auth outage, not a degraded feature. Migrate before rebuilding, never after, and set VAULTCHAT_LOOKUP_PEPPER or the column stays NULL and every refresh falls back to a 500-row scan.

Two databases share one name

The host cluster held a vaultchat database left over from the July 2026 cutover, stuck at migration 060, and reading it made prod look 66 migrations behind — which already misled one deploy. Defused 2026-09-07 by renaming it to vaultchat_stale_20260722 and disabling the host pgbouncer. Production is the container pair: go-api → pgbouncer → postgres.

Two proxies must agree

A path has to exist in both the Caddyfile and cmd/api/main.go to be live. This has bitten before — VaultView's revoke endpoint 404'd until uploads.go caught up. The generic catch-all message “route not migrated to go backend” is the symptom.

Routing is dark until fed

POST /nav/route stays down until an OSM extract is dropped into valhalla/custom_files/; first boot then builds tiles for several minutes. Chat, calls and media are unaffected — navigation is the only surface that fails.

Mobile toolchains never run on the server. Rust and Kotlin compile only into the APK; Docker builds Go inside the image. There is no host Go, no host Rust, and no reason for either to appear on the box.
