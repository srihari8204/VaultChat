Check two things on a test instance first.

Is the public IP on the instance's own interface (ip -4 addr)? If Utho NATs it, set TURN_EXTERNAL_IP to PUBLIC/PRIVATE for coturn and keep LiveKit's node_ip at the public address, or relayed calls fail.

Do Cloud Firewall rules also filter VPC traffic? If they do, add the private ports above as rules limited to the VPC range, including the two for Go Live when it moves.

Build order on Utho

Each phase needs the one before it. Phase 4 is the launch plan's bring-up steps 2 to 14, unchanged apart from the addresses.

  1. Account and a throwaway test instance

    1–2 days

    Open the account, add SSH keys, create an API token. Start one small hourly instance in inmumbaizone2 and answer the questions in Ask Utho by testing: public IP on the interface, a UDP range rule, VPC reachability, fio on a block volume, ping from Indian mobile networks. Delete it afterwards.

  2. Network

    console or Terraform

    Create crazzychat-vpc (10.20.0.0/24) and the four Cloud Firewalls with the rules above. Click-by-click in Buy.

  3. Instances and volumes

    all four

    Create the four instances on Ubuntu 24.04 if Utho lists it, otherwise 22.04, with SSH keys, the VPC and their firewall, on hourly billing while you build. Attach the two 1 TB volumes and move Docker's data directory onto them as shown in Storage. Record every public and VPC address. Click-by-click in Buy.

  4. Bring-up

    launch plan steps 2–14

    Host preparation, database, schema, standby, API, call media, broadcasting, router, edge and TLS, backups and monitoring, in that order. Put the Utho addresses into changes S1 to S4, and apply the NAT setting if the test instance showed one.

  5. Verify and measure

    CORE-1

    /health, /ready, /build against scripts/fingerprint-go.sh for the tree you deployed, the boot log line services: calls, core, family, games, golive, maps, shopbook, TURN from outside, a call and a broadcast between two phones, then scripts/bench/run.sh before real data lands.

  6. Cut over from Hetzner

    one maintenance window

    The sequence in Migration.

  7. Switch billing

    after a stable week

    Move the instances from hourly to monthly or longer billing (billingcycle accepts monthly, 3month, 6month, 12month). Keep hourly until the plan sizes are proven.

Optional: the network and instances as code

Utho's Terraform provider (uthoplatforms/utho) covers VPCs, firewalls, instances, load balancers and DNS. Firewall rules and block volumes are not in it, so add those in the console or through the API. Plan IDs come from Utho's plan list.

terraform {
  required_providers {
    utho = { source = "uthoplatforms/utho" }
  }
}

provider "utho" { token = var.utho_token }

resource "utho_vpc" "cc" {
  dcslug  = "inmumbaizone2"
  name    = "crazzychat-vpc"
  planid  = var.vpc_plan_id
  network = "10.20.0.0"
  size    = "24"
}

resource "utho_firewall" "fw" {
  for_each = toset(["fw-core", "fw-db", "fw-media", "fw-live"])
  name     = each.key
}

locals {
  servers = {
    "core-1"  = { plan = var.plan_core,  fw = "fw-core",  backup = true  }
    "db-2"    = { plan = var.plan_db,    fw = "fw-db",    backup = false }
    "media-1" = { plan = var.plan_media, fw = "fw-media", backup = false }
    "live-1"  = { plan = var.plan_live,  fw = "fw-live",  backup = false }
  }
}

resource "utho_cloud_instance" "cc" {
  for_each        = local.servers
  name            = each.key
  dcslug          = "inmumbaizone2"
  image           = var.image           # ubuntu-24.04-x86_64 if listed, else ubuntu-22.04-x86_64
  planid          = each.value.plan
  vpc_id          = utho_vpc.cc.id
  firewall        = utho_firewall.fw[each.value.fw].id
  enable_publicip = "true"
  enablebackup    = each.value.backup
  billingcycle    = "hourly"
  sshkeys         = var.ssh_key_ids
  root_password   = var.root_password   # required by the provider; password SSH stays off
}

Order on Utho

  1. Deploy the preparation

    CORE-1

    No new settings. The one new behaviour is that each background job holds a Postgres advisory lock while it runs; watch idle in transaction in pg_stat_activity for a day. Then apply migration 139 (inert until a role gets a password).

  2. Switch access tokens to Ed25519

    CORE-1

    Mount the private key, restart go-api, run the two-phone check with a phone that was logged in before, then set ACCESS_TOKEN_HS256=off.

  3. Move features out

    2–5 days each

    Maps first, as the pilot, then Go Live onto LIVE-1 with the two firewall rules in Network, then Games, ShopBook, Family Space and Calls. Each gets a Caddy block that falls back to core, so pointing its paths back at core undoes the move.

  4. Grow a server when one runs short

    as needed

    Maps (Valhalla needs the most memory) is the first service to get its own instance, then ShopBook. Any service can also run a second copy behind Caddy; the job locks keep its background work single-run.

Moving from Hetzner to Utho

The hostnames stay, so installed apps follow the DNS change. The data to move is small; most of the work is keys and checks.

  1. Copy what cannot be recreated

    Both env files, docker-compose.box.yml, secrets/ (including the access-token private key once it exists), .offsite-key, the RLS and svc_* role passwords, HLS_TICKET_SECRET and INTERNAL_SERVICE_KEYS if set, /etc/letsencrypt, the deployed LiveKit YAMLs, the admin panel files. Put the keys in a password manager before anything else. Keep the same access-token key on Utho, so tokens issued on Hetzner stay valid through the cutover.

  2. Build Utho alongside

    Phases 1 to 5 above. Test with curl --resolve api.corefinite.com:443:<CORE-1 IP>, and with a staging app build for device tests.

  3. Move the bulk data directly

    Over SSH from Hetzner to Utho: Valhalla tiles (9.8 GB), and MinIO's broadcast segments (5.8 GB) only if you want old replays. At 100 Mbps, 16 GB takes about 22 minutes. The database dump was 3.4 MB compressed in September.

  4. Lower DNS TTLs

    api, stream, admin and turn to 60 seconds a day ahead.

  5. Maintenance window

    Stop go-api on Hetzner, take the final dump, restore on CORE-1, compare the migration ledger (the same highest number on both sides, 139 once the service roles are applied) and row counts, and re-seed DB-2.

  6. Switch DNS

    api, stream and admin to CORE-1; turn to MEDIA-1; update the origin for the proxied names in Cloudflare.

  7. Verify

    /build matches the deployed tree, then the two-phone smoke test on Utho.

  8. Keep Hetzner, then close it

    Leave it stopped for 14 days as a rollback, then cancel it and wipe the disks. JumpServer, Portainer, Beszel and SearXNG share that box but CrazzyChat does not need them; bring SearXNG only if you use SEARXNG_URL.
