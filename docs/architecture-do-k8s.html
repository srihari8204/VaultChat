CrazzyChat on Kubernetes

VaultChat runs today on one Hetzner box — Go API, Postgres, Redis, MinIO, two LiveKit SFUs and coturn sharing a single kernel and a single failure domain. This is the move to DigitalOcean Kubernetes, sized for 100k users and 20k concurrent WebSocket connections, under the CrazzyChat brand.

Two planes, one of which never touches the load balancer

This is the idea the whole design turns on. API traffic and call signalling go through Cloudflare and the DigitalOcean load balancer like any web service. Call media does not — it goes straight from the phone to a media node's public IP.

An SFU forwards packets; putting a load balancer in front of it would place a proxy in the path of every RTP packet and break ICE, because the candidates a client receives advertise the node's own address. DigitalOcean load balancers do not carry UDP in any case.

Four node pools, because the workloads have four different shapes

A socket server is memory- and file-descriptor-bound. An SFU is bandwidth-bound and needs host networking. A room-composite recorder runs headless Chrome and is the only genuinely CPU-bound thing in the stack. Co-tenanting them is what the current box does, and it is the reason a large call can make the database wobble.

egress c-8vcpu-16gb 0 → 4 workload=egress:NoSchedule LiveKit egress ×2 — SYS_ADMIN, 4-CPU hard floor

Calling and Go Live stay on separate pools on purpose. The backend already refuses to start if the two LiveKit deployments share credentials — that isolation is enforced in code, and putting them on shared nodes would quietly re-couple the resource blast radius it exists to prevent. The egress pool scales to zero, so the most expensive droplet class only bills while someone is actually broadcasting.

One failure domain becomes four

Nothing about the current stack is wrong for the scale it was built at. What it cannot do is survive losing the machine, or absorb a spike in one subsystem without the others feeling it.

Nine things in the code break on Kubernetes

These came out of reading the source, not from a checklist. Most are small. All of them are load-bearing, and four share a property that makes them worse than they look: they fail silently. Nothing errors, nothing restarts, and the symptom surfaces far from the cause.

1

vaultchat-backend-go/cmd/api/main.go:325

No graceful shutdown.

The server was started with log.Fatal(srv.ListenAndServe()) — no SIGTERM handler at all. On one long-lived box that costs a few seconds at deploy time. Under an orchestrator every rolling update, autoscale-down and node drain runs this path, so it stops being occasional and starts dropping live conversations routinely. Fixed: signal handling, a drain delay for load-balancer deregistration, an explicit hub disconnect, then srv.Shutdown. Note http.Server.Shutdown does not close hijacked connections — which is every WebSocket — so the hub drain is required, not decorative.

2

internal/routes/auth.go:119 — trustedProxyNets

Rate limiting collapses into one global bucket.

The default trusted-proxy list is 127.0.0.0/8,::1/128,172.28.0.0/16,172.17.0.0/16 — the Docker bridges the compose files pin. A DOKS pod network is 10.244.0.0/16, so the ingress pod is not trusted, and authClientIP returns the ingress pod's own address for every request on the cluster. Per-IP limits on OTP issuance and account lookup then share a single bucket, and one person can lock everybody out of signing in. Fix: set TRUSTED_PROXIES to the real pod and VPC CIDRs. This is configuration, but getting it wrong is a security regression rather than an outage.

3

internal/redisx/redisx.go:19

The Redis client could not speak TLS.

redis.NewClient set only Addr and Password, and today's deployment runs with no Redis password at all. DigitalOcean replaced Managed Redis with Managed Valkey, which requires TLS. Every call would fail at boot — and because the socket layer fails open to local maps, the result is not an outage: cross-replica fan-out silently stops, presence lies, and each pod runs as an isolated island that looks healthy. Fixed: REDIS_URL (rediss://) via redis.ParseURL, plus a REDIS_TLS switch for the discrete host/port form.

4

livekit/livekit.yaml:50 · livekit/golive.yaml:59

The node's public IP is hardcoded.

Both configs pin node_ip: 65.21.229.167, and LiveKit reads its config verbatim — it does not expand ${VAR}, which this repo already learned once when a placeholder reached the server as fourteen literal characters. On a cluster every node has a different address and nodes get replaced, so every SFU pod would advertise a Hetzner IP in its ICE candidates and no media would ever connect. Fix: an initContainer reads the node's address from the DigitalOcean metadata service and passes it as --node-ip, which sidesteps the no-expansion limitation entirely.

5

internal/realtime/server.go:166 · cluster.go:153

The obvious autoscaling metric is fleet-wide, not per-pod.

sockets_online calls OnlineCount(), which under REDIS_ADAPTER=1 — production — returns a Redis SCARD. Every replica reports the identical fleet total. An autoscaler averaging that across pods gets the fleet total back and jumps straight to max replicas on its first evaluation. The trap is that it looks perfectly correct in a one-pod staging test, where local and fleet are the same number. Fixed: a new sockets_local gauge that is always process-local, with a test pinning the distinction.

6

media DaemonSets — dnsPolicy

Host-networked pods cannot resolve cluster DNS by default.

A hostNetwork pod uses the node's resolver and cannot see *.svc.cluster.local unless dnsPolicy: ClusterFirstWithHostNet is set. Omit it and every LiveKit egress webhook lookup fails: a broadcast is created, a room exists, and its status never leaves "starting", because the webhook is the only signal that recording began. Fix: set it on all three DaemonSets — and CI now fails any chart that uses host networking without it.

7

internal/routes/uploads.go:47

Attachments can fall back to local disk.

When no object store is configured, uploads write to a local directory. That is correct for dev and for a single-box self-host, and quietly destructive behind a Deployment: each replica writes to its own filesystem, so a file succeeds on the pod that received it and 404s from every other. It presents as "some images don't load", intermittently, in proportion to replica count. Fixed: a REQUIRE_OBJECT_STORE boot guard — the process refuses to start rather than serve a storage layer that loses files.

8

internal/storage · internal/livekit · internal/db

Hardcoded fallbacks point at the old box.

S3_PUBLIC_ENDPOINT defaults to the Hetzner IP and PlaybackBase() falls back to a literal api.corefinite.com, so an unset variable hands clients URLs resolving to the server being decommissioned. Separately, the database DSN interpolated the password into a URL unescaped — fine for vaultchat_dev, broken by the character set a managed provider generates — and set no sslmode, so TLS was negotiated but never verified. Fixed: credentials escaped, sslmode explicit, origins required.

9

internal/jobs · broadcast_reaper · golive_reaper · shopbook_jobs

Only one background sweep takes a lock.

The realtime janitor guards itself with vc:janitor:lock. The other four schedulers start unconditionally in every replica — at 30 pods, each sweep runs thirty times. ShopBook documents itself as idempotent because "already sent" is derived from the notification inbox, but that is restart idempotency, which is not the same property as safety under concurrent execution. Open: audit each tick, then either prove it atomic or wrap it in the lock the janitor already uses.

Two things that are already right

Worth recording so nobody "fixes" them. /health returns 200 unconditionally — it reports database and Redis state in the body but never in the status code — because a restart does not fix a database outage. It is safe as a liveness probe; it is just not free, since it pings both dependencies on every call, so a probe-free /livez was added rather than replacing it. And /ready already existed, already 503s on database loss, and already treats Redis loss as degraded-not-down. That is exactly the right split, and it is the single biggest reason this migration is a week of work rather than a month.

Cutover

This is a live system with real users and a database at migration 126. The cluster gets built and proven alongside it; only the last phase touches production.

  1. Drop DNS TTLs

    24 hours ahead. Cloudflare is proxied, so clients never see the origin address — the flip is invisible to them.

  2. Start logical replication

    Enable wal_level=logical on the source and let DigitalOcean's external-database import run the initial sync and continuous catch-up.

  3. Pause writes, wait for zero lag, promote

    Minutes, not hours. Do not reuse the nightly backup script for this — it deliberately excludes message_bodies, and would silently migrate a database with no message ciphertext in it.

  4. Start Valkey empty

    Presence, adapter state and rate-limit counters are all ephemeral and rebuild on reconnect. There is nothing to migrate.

  5. Flip the origin records

    api.corefinite.com and api.crazzychat.com both point at the new load balancer.

  6. Repoint TURN

    turn.* round-robins across the media node IPs. Installed apps pick this up automatically — TURN hosts are handed out at runtime by the API, not compiled in.

  7. Smoke test on mobile data

    A 1:1 call, a group call on the SFU, a broadcast that produces a playable HLS URL, and an attachment round-trip — from a phone on a carrier network, not the office wifi, so ICE and TURN are actually exercised.

The domain cannot be swapped, only added to

constants/server.ts hardcodes https://api.corefinite.com as a compile-time constant, and the Android App Links filter in app.json is pinned to the same host. Every APK already installed has that baked in. So api.corefinite.com keeps serving from the new cluster indefinitely, on the same certificate as api.crazzychat.com. New builds flip the constant; old installs never notice the move.
