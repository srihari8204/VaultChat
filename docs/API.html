VaultChat API Reference

One unversioned JSON API and one Socket.IO namespace, both served by a single Go process at https://api.corefinite.com. Every route below was extracted from the Register…(mux) calls in vaultchat-backend-go/internal/routes/ — if a path is not here, it is not served, and the catch-all answers “route not migrated to go backend”.

01

Conventions

httpx.go is the contract

Transport

  • Base URL — https://api.corefinite.com. No version prefix; the API is versioned by deploy, not by path.
  • Content type — application/json; charset=utf-8 both ways, except attachment bytes (presigned PUT straight to S3) and HLS segments.
  • Request body cap — 2 MB, enforced by a LimitReader. An empty body decodes as {} rather than erroring.
  • Client timeout — 30 s per request, 15 s for /auth/refresh. Uploads (FormData) and caller-supplied AbortSignals are exempt.
  • Trailing paths — Go 1.22 ServeMux patterns. {id} is a single segment; {file...} is a wildcard tail.

Standard headers

HeaderDirectionMeaning
Authorization→Bearer <accessToken>. HS256, claims {sub, email}.
X-Device-Id→Stable per-install id from the OS keystore. Lets the server tell a resumed client from a cold start — it drives the cold-sync cap. Optional; a client without one syncs uncapped.
x-admin-key→Admin console only. Constant-time compared against ADMIN_KEY.
X-Internal-Key→/internal/emit and /internal/chat-event. Caddy 404s these paths from outside regardless.
Accept→application/json.

Authentication schemes

Five, and they do not overlap. A route accepts exactly one.

SchemeApplies toMechanismFailure
bearer351 routes — everything user-facing HS256 access token in Authorization. Verified per request; JWT_SECRET is read lazily but the process refuses to boot if it is empty. 401 Missing Bearer token · 401 token_expired · 401 invalid_token
admin key25 routes under /api/admin Shared secret in x-admin-key, constant-time compared. Client IP resolved from cf-connecting-ip → x-real-ip → x-forwarded-for for the audit row. 401 Invalid admin key · 503 if ADMIN_KEY is unset
LiveKit JWT2 egress webhooks under /internal/ LiveKit signs the request with the API secret and includes a body SHA-256 in the token; both the signature and the body hash are checked. 401, body discarded
HMAC ticketGET /broadcasts/{id}/hls/{file...} Per-broadcast HMAC-SHA256 ticket in the query string, bucketed by time window. The playlist is rewritten so each segment carries a fresh ticket. Deliberately outlives an access token — a player cannot refresh one mid-stream. 403
Ed25519POST /games/notify Signature verified against GAMES_NOTIFY_PUBLIC_KEY_PEM (or …_FILE). The games deployment holds the private half; VaultChat never does. 401

Error envelope

Two shapes exist, and which one you get is decided by the module, not the status code.

// httpx.Err — everything except the auth module
{ "error": "Not a member of this chat" }

// with extra fields merged in at the top level
{ "error": "Slow mode is on", "retryAfter": 12 }

// authEnvErr — /auth/* only, machine-readable code
{ "error": { "code": "rate_limited",
            "message": "Too many requests. Try again later." } }
Do not branch on message text outside /auth. Only the auth envelope carries a stable code; the flat shape's string is prose and has changed before.

Timestamps & numbers

  • Every timestamp marshals as "2026-09-12T08:41:03.000Z" — UTC, always three millisecond digits. This matches what node-pg emitted, so clients written against the Node backend parse Go responses unchanged.
  • Nullable timestamps are null, never omitted.
  • bigint ids (messages) are serialised as strings, not numbers — they outgrow IEEE-754 safe integers.
  • Query integers parse like JS parseInt: leading sign and digits, trailing junk ignored. "20abc" is 20.

Pagination & idempotency

  • Message listing is cursor-based on message id: before / after + limit, capped server-side.
  • Delta sync uses a monotonic since cursor with a nextSince in every response — never a page number.
  • Sends carry a client-generated clientId. A partial unique index on (chat_id, sender_id, client_id) makes the retry idempotent, which is what lets the offline outbox re-flush without duplicating.

Status codes in use

CodeWhen
200Success, including creates — the API does not use 201.

401Missing/expired/invalid credential. Three distinct strings; the client only treats these as terminal on /auth/refresh.

Auth & session

20 endpoints · 17 unauthenticated by necessity

Two entry paths — email OTP and Google — both ending in the same token pair. Phone OTP and the onboarding variant exist alongside them for the encrypted-PII signup flow. After that, everything is the refresh dance.

POST/auth/send-otppublicthrottled per identifier and per IP

Issues a one-time code to an email address. Two independent rate limits apply; both answer 429 with the auth envelope, and a burned code answers 429 Too many attempts. Request a new code. rather than silently accepting retries.

FieldTypeNotes
emailstring requiredNormalised before hashing into the attempt bucket.
POST/auth/verify-otppublicissues the token pair

Exchanges a valid code for a session. Records the attempt in auth_attempts with the resolved client IP whether it succeeded or not.

// 200
{
  "accessToken":  "eyJhbGciOiJIUzI1NiIs…",   // HS256, {sub, email}
  "refreshToken": "…",                       // single-use, rotates
  "user": { "id", "email", "name", "phone", "photoUrl",
             "vaultId", "status", "createdAt" }
}
POST/auth/refreshpublicsingle-use · rotates

Takes { refreshToken }, revokes it, and returns a fresh pair. Because rotation is single-use, a client must serialise refreshes — a dozen requests 401'ing at once on app resume must share one in-flight call, or the first rotation invalidates the token the rest are about to present.

Only 401 and 403 mean the session is over. The client distinguishes three outcomes — ok, terminal, transient — because treating a 503 during a deploy, a captive portal's HTML 200, or a dropped connection as "revoked" logs real users out and sends them back through onboarding. Anything that is not an explicit rejection keeps the credentials.

Migration 127 adds refresh_tokens.token_lookup; without VAULTCHAT_LOOKUP_PEPPER set, the column stays NULL and every refresh silently degrades to a 500-row scan.

Media & uploads

bytes never transit go-api

Two paths, chosen by size. Both hand the client a presigned URL and keep the service out of the byte stream; the attachment row is created first so an abandoned upload is still attributable and sweepable.

POST/uploads/presignbearer

Single-shot. Returns a 15-minute PUT URL bound to the declared MIME type.

// request
{ "filename", "mime", "size", "viewOnce", "purpose" }

// 200
{ "id": "…", "uploadUrl": "https://…", "key": "…" }

413 File too large (max N bytes) above UPLOAD_MAX_BYTES; 503 Object storage not configured if the S3 credentials are absent.

POST/uploads/multipart/*bearer

Resumable, for large files on a network that drops.

{id}/partsGET — which parts the store already has. This is what makes resume work after a restart.
completeAssembles the object.
abortCancels and deletes the parts.

Lifecycle

GET/uploads/{id}Presigned read URL. Owner-asserted: 403 Forbidden if the row belongs to someone else, 404 Not found if it does not exist.
POST/uploads/{id}/viewedMarks a view-once item consumed.
POST/uploads/{id}/revokeRevokes access to an already-sent attachment.
POST/uploadsLegacy direct-body upload, still served.

Retention

Attachments are swept by media-retention on the same tick as messages, scoped by delivery state and MEDIA_TTL_DAYS/MEDIA_TTL_HOURS. Objects whose purpose the server cannot classify are never deleted by design — instead a Prometheus gauge counts them, because "safe to retain" without observability becomes unbounded storage nobody is looking at.

05

Key distribution

X3DH prekeys

The only server role in the end-to-end path: hold public prekey bundles and hand out one one-time prekey per fetch. Private halves never leave the device.

POST/user/keybundlebearer
{
  "identityKey":  "<packed b64>",
  "signedPreKey": { "keyId": 1,
                     "publicKey": "…",
                     "signature": "…" },
  "oneTimePreKeys": [ { "keyId": 7, "publicKey": "…" }, … ]
}
GET/user/{id}/keybundlebearer
{
  "identityKey":  "…",
  "signedPreKey": { "keyId", "publicKey", "signature" },
  "oneTimePreKey": { "keyId", "publicKey" } | null
}

One OTPK is consumed per fetch and never returned again. null means the peer's supply is exhausted — the session still forms, with reduced forward secrecy for that first message.

GET /user/{id}/keybundle and GET /user/{id}/identity are dispatched through a GET /user/ subtree handler rather than registered as patterns — they collide with /user/by-vault/{vaultId} in ServeMux precedence, which panics at registration. Their behaviour is identical; only the registration differs.

A changed identity key is surfaced, never silently accepted. A peer who reinstalls gets a new identity key — and so does an attacker substituting their own. The protocol cannot tell them apart, so the client records peerIkHex per session and raises the change to the user. Without it a key substitution is invisible: the padlock still shows, and the ratchet still works, against the wrong person.

Realtime

Socket.IO · /socket.io/

Handshake

io(SERVER_URL, {
  transports: ['websocket'],
  // a FUNCTION, not an object: an object captures one
  // token at construction and re-presents it forever
  auth: cb => cb({ token: '<accessToken>' })
})
  • The JWT middleware runs before connection. A missing token is auth_required; an invalid one returns the same token_expired / invalid_token strings as the REST path, so the client can reuse one refresh decision for both.
  • The admin console authenticates with { adminKey } instead and joins the admin room.
  • A Bearer header is accepted as a fallback when the handshake auth object is absent.
  • Authorisation is re-checked on roster changes — a removed member's existing connection loses access rather than keeping what it held at connect time.

Rooms

chat:<chatId>Joined via join_chat, membership-checked. Fan-out filters blocked senders and ghost mode.
<userId>Per-user room; every device of that account.

Presence is cluster state, not process state. vc:pres:<uid> counts sockets per node and vc:node:hb:<node> expires, so a crashed node's users stop counting as online within the TTL. This matters beyond a green dot: presence gates call wake-push suppression, and a stale "online" is a silently missed call.

Error reference

exact strings, matched to the Node contract
StatusBodyRaised by
401{"error":"Missing Bearer token"}No Authorization header, or one that is not Bearer ….
401{"error":"token_expired"}Valid signature, past exp. The client refreshes and retries once.
401{"error":"invalid_token"}Bad signature, wrong algorithm, or a missing sub claim. Only HS256 is accepted — an alg swap is rejected before verification.
401{"error":"Invalid admin key"}/api/admin/* with a wrong x-admin-key.
403{"error":"Blocked"}Sending into a chat with a block in either direction.
403{"error":"Forbidden"}Attachment owned by another user.
404{"error":"Not found"}Row absent.
404{"error":"route not migrated to go backend"}The catch-all. Means the path is registered in Caddy but not in cmd/api/main.go — a deploy problem, not a client one.
413{"error":"File too large (max N bytes)"}Presign above the cap.
423{"error":{"code":"locked","message":"Too many attempts. Try again in Ns"}}MPIN or OTP lockout.
429{"error":"Slow mode is on","retryAfter":N}Group slow mode.
429{"error":{"code":"rate_limited","message":"…"}}Auth throttling.
503{"error":"Object storage not configured"}S3/R2 credentials missing.
503{"error":"ADMIN_KEY not configured on server"}Admin routes with no key set — fails closed, not open.

Health probes

EndpointAlwaysBody
GET /health200{status, db, redis, uptime} — status is degraded when either dependency is down. Never 503: a restart does not fix a database outage, and an orchestrator must not loop on one.
GET /go-health200Alias kept from the strangler period.
GET /ready200 / 503{ready, db, redis, uptime}. Postgres unreachable → 503. Redis down does not fail readiness — the limiter falls back in-process and the socket layer to local maps, so it is a degradation reported in the body, not an outage.
GET /internal/metrics200Prometheus text. In-network only; Caddy 404s /internal/* from outside.

Both probes bound their checks at 2 seconds. They used to inherit the request context, so a database that was wedged rather than down left the one request that must always answer hanging as long as the client would wait.
