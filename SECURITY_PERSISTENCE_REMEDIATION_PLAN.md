# VaultChat — Data-Persistence & Storage-Boundary Remediation Plan

**Target branch:** `hetzner-deploy`
**Work branch:** `claude/vaultchat-security-audit-qgxecb`
**Production:** `vaultchatprod01` (`65.21.229.167`) → `https://api.corefinite.com`, Go-first Docker stack
**Source audit:** "Why does my data come back after uninstall + reinstall?" (findings F-1 … F-12)
**Status:** plan only — nothing in this document has been implemented.

---

## 0. What this plan fixes

Reinstalling the app on the same device brings back photos, videos, documents,
audio, messages and profile images. Three independent mechanisms cause this,
and each is sufficient on its own:

| ID | Mechanism | Fixed in |
|----|-----------|----------|
| **A** | `/Android/media/com.vaultchat.app/**` is not deleted by Android on uninstall, and the app stores all media + full encrypted backups there | Phase 3, Phase 2 |
| **B** | `GET /chats/delta?since=0` re-exports the complete server-side history after login; `DELETE_ON_DELIVERY` is off, so the server keeps every message body forever | Phase 1 |
| **C** | `android:allowBackup="true"` with no exclusion rules — Google restores the plaintext SQLite cache, AsyncStorage media keys and `files/` | Phase 2 |

The plan is sequenced so the **cheapest, highest-impact, zero-app-release work
lands first** (Phase 1 is server-only and deploys to the Hetzner box in
minutes), and the invasive client storage migration lands last, behind a
staged APK rollout.

## 1. How this plan fits the `hetzner-deploy` deployment

Everything below is written against the actual production topology documented
in `DEPLOY_STEPS.md` and `DEPLOY_OPERATIONS.md`:

```
Cloudflare (proxy, WS on, SSL Full)
  └─► host nginx :443  (/etc/nginx/sites-enabled/vaultchat)
        └─► Caddy 127.0.0.1:8095
              └─► go-api :4000   (all REST modules + Socket.IO + internal/jobs)
```

Constraints this plan respects:

- **Go-first.** All server behaviour changes land in `vaultchat-backend-go/`.
  The Node `api` container is **not deployed** — it exists only under
  `--profile legacy` for emergency rollback and for running `migrate.js`.
- **The `dc` alias is mandatory.** Every command below assumes:
  ```bash
  alias dc='docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.box.yml'
  ```
  Dropping the `-f` flags re-exposes bench ports and starts kafka.
- **Migrations run through the legacy image**, one-shot:
  `dc --profile legacy run --rm api node migrate.js up`.
  Highest existing migration is `067_rls_chats_insert.sql`, so **new migrations
  start at `068`**.
- **Secrets live in `vaultchat-backend/.env`**, which compose feeds to both
  `go-api` and `vaultlens-worker`. New flags are added there, not baked into
  images.
- **Mobile toolchains never run on the box.** Rust and Kotlin are mobile-only;
  the server image is `golang:1.26-alpine` → `alpine:3.20`.
- **`/android` is gitignored** and regenerated by `expo prebuild`. Any
  manifest change **must** be an Expo config plugin under `plugins/`, or it
  will be silently lost on the next EAS build. This is the single most
  important packaging constraint in this plan.

## 3. Phase 0 — Pre-flight (do this first, it is cheap)

### 3.1 Measure the real blast radius on a device

Before writing anything, quantify what actually survives on a real handset.
Run against a device that has used the app for a while:

```bash
adb shell ls -la /sdcard/Android/media/com.vaultchat.app/VaultChat/Media/
adb shell du -sh /sdcard/Android/media/com.vaultchat.app/
adb shell ls -la /sdcard/Android/media/com.vaultchat.app/VaultChat/Databases/
adb shell ls -la /sdcard/Android/media/com.vaultchat.app/VaultChat/Media/.Thumbs/ | wc -l
```

Then uninstall, reinstall, and re-run. Record which paths persisted. This
becomes the acceptance baseline for Phase 3 (§10).

### 3.2 Confirm the shipped manifest

`/android` is gitignored, so the only way to know what shipped is to read the
built artifact:

```bash
# on a dev machine, against the release APK
aapt2 dump xmltree app-release.apk --file AndroidManifest.xml | grep -i -A2 allowBackup
```

Expected today: `allowBackup=true`, no `dataExtractionRules`, no
`fullBackupContent`. Confirm before Phase 2 so the fix is verifiable.

### 3.3 Product decisions required from the owner

These change the shape of the work and cannot be inferred from the code:

| # | Decision | Options | Recommendation |
|---|----------|---------|----------------|
| **D1** | Should media survive uninstall at all? | (a) never — sandbox only; (b) opt-in browsable folder; (c) keep as today | **(a)** for the default, with (b) as an explicit, disclosed setting |
| **D2** | What happens to media already on disk in the old external location when the fixed app launches? | (a) migrate into sandbox then delete; (b) delete outright; (c) leave and ignore | **(a)** — migrate, then delete; never silently destroy the user's photos |
| **D3** | Server message retention | (a) delete-on-delivery + max-age; (b) max-age only; (c) unlimited | **(a)** with `MAX_AGE_DAYS` as a safety net |
| **D4** | Backup key custody | (a) server-managed (today); (b) user passphrase; (c) 64-digit recovery key | **(c)** as the default, (a) allowed only if backups exclude identity keys |
| **D5** | Do E2EE identity keys ever belong in a backup? | yes / no | **No.** This is the single most consequential item in the audit |

**Do not start Phase 3 until D1 and D2 are answered.**

## 4. Phase 1 — Server: retention + delta hardening

**Findings addressed:** F-5 (unbounded full-history export, indefinite
retention), F-2 (server half of the backup-key problem).
**Deploys to:** Hetzner box, `go-api` only. **No app release required.**
**Risk:** low, but see the data-loss warning in §4.1.

### 4.1 ⚠️ Read before enabling retention

Turning on `DELETE_ON_DELIVERY` **permanently nulls message bodies** once every
recipient has acknowledged delivery. This is the correct privacy posture and it
is exactly what makes reinstall stop resurrecting chats — but it is
irreversible for already-purged rows, and any user whose only copy of a
conversation was the server will lose it.

The purge job (`internal/jobs/jobs.go`) is already written, batched and
boot-verified. It is gated off. Enabling it is a **policy decision (D3)**, not
an engineering task.

Roll it out in this order:
1. Set a long `DELETE_ON_DELIVERY_MAX_AGE_DAYS` first (e.g. 365) with
   delete-on-delivery still **off**. Observe.
2. Enable delete-on-delivery with a generous grace period.
3. Tighten the max-age over subsequent releases.

### 4.2 Work items

| # | Item | Where | Notes |
|---|------|-------|-------|
| 1.1 | Enable retention | `vaultchat-backend/.env` | `DELETE_ON_DELIVERY`, `DELETE_ON_DELIVERY_GRACE_SEC`, `DELETE_ON_DELIVERY_MAX_AGE_DAYS` — all already read by `internal/jobs` |
| 1.2 | Floor the delta cursor for unknown devices | `internal/routes/chats.go` (`chatsDelta`) | A `since=0` request from a device id the server has never seen should return a bounded recent window, not the full history, unless the client presents a step-up assertion |
| 1.3 | Bind sync to a registered device | `internal/routes/chats.go`, `migrations/005_devices.sql` (existing table) | Reuse the existing device registry; a cold `since=0` from a new device id raises a security event |
| 1.4 | Rate-limit + alert on bulk delta drains | `internal/httpx`, `internal/metrics` | A single session paging 500× is the exfiltration signature; emit a metric and a `security_events` row (`migrations/036_security_events.sql` exists) |
| 1.5 | Surface "new device synced your history" | `internal/routes/user.go` + existing security-events UI | Detection is worthless if the user never sees it |
| 1.6 | Stop escrowing identity keys | server side of F-2 — see Phase 3.4 | Server change is only the key-issuance policy; the bundle contents are client-side |
| 1.7 | Migration `068_device_sync_cursor.sql` | `vaultchat-backend/migrations/` | Records first-sync-per-device so 1.2/1.3 have state to read |

### 4.3 Deploy to the box

```bash
# from a dev machine
git checkout hetzner-deploy && git pull
# merge the phase-1 PR, then on vaultchatprod01:

cd /home/srihari/vaultchat
git pull

# 1. new env vars
vi vaultchat-backend/.env        # DELETE_ON_DELIVERY=... etc.

# 2. migration 068
dc --profile legacy run --rm api node migrate.js up

# 3. rebuild Go only (Docker compiles it; no host Go toolchain)
dc up -d --build go-api

# 4. verify
dc logs go-api --tail 30                       # expect: [delete-on-delivery] ENABLED
curl -s http://127.0.0.1:8095/health ; echo    # {"db":true,"redis":true,"status":"ok",...}
curl -s https://api.corefinite.com/health ; echo
```

### 4.4 Verification

- `dc logs go-api | grep delete-on-delivery` shows `ENABLED` and, after the
  first sweep interval, `purged N delivered message bodies`.
- A test account's older delivered messages return `content: null` from
  `GET /chats/delta`, while clients that already cached them still render
  (this is the `COALESCE(excluded.content, messages.content)` guard in
  `lib/localDb.ts` — it is correct and must not be removed).
- A `since=0` request from an unregistered device returns a bounded window and
  writes a `security_events` row.
- Contract suite still green: `BASE_URL=http://127.0.0.1:8095 node vaultchat-backend/contract/run.js`.

### 4.5 Rollback

Retention: set `DELETE_ON_DELIVERY=false` and `dc up -d go-api`. **Already-purged
bodies do not come back** — this is why §4.1 sequencing matters.
Delta hardening: revert the commit, `dc up -d --build go-api`. Per-route
fallback to Node remains available via `--profile legacy` as documented in
`DEPLOY_OPERATIONS.md`.

### 4.6 Compatibility with the APK in the field (`versionCode 16`)

All Phase 1 changes are backward compatible. An old client that receives
`content: null` for a purged message keeps its local copy. An old client with
no device id must still be allowed to sync — gate 1.2/1.3 to **warn-only** for
the first release, and enforce once the fixed APK has meaningful adoption.

## 5. Phase 2 — Android backup lockdown

**Findings addressed:** F-3 (Auto Backup unrestricted), F-11 (legacy storage
permissions).
**Deploys as:** an Expo config plugin + `app.json` edit → new APK.
**Risk:** very low. No server change, no data migration.

### 5.1 Why this must be a config plugin

`/android` is gitignored and regenerated by `expo prebuild --clean` on every
EAS build. A hand-edited `AndroidManifest.xml` **will be silently discarded**.
The repo already follows this pattern correctly —
`plugins/withAndroidFeatures.js` uses `withAndroidManifest` — so the new plugin
follows the same shape and is registered in the `plugins` array of `app.json`.

### 5.2 Work items

| # | Item | Where |
|---|------|-------|
| 2.1 | New plugin `plugins/withBackupLockdown.js` | sets `android:allowBackup="false"` and `android:hasFragileUserData="false"` on `<application>` |
| 2.2 | If any backup is to be retained, ship explicit allow-lists instead | `backup_rules.xml` (API ≤ 30) **and** `data_extraction_rules.xml` (API 31+) — both are required; shipping only one leaves the other API range on defaults |
| 2.3 | Register the plugin | `app.json` → `expo.plugins` |
| 2.4 | Drop legacy storage permissions | `app.json` → remove `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE` (the app-specific media dir needs neither; this also reduces Play policy exposure) |
| 2.5 | iOS parity | mark `files/media`, `files/VaultBeam`, `files/note_attachments` and the SQLite file as excluded-from-backup so iCloud does not become the iOS equivalent of F-3 |
| 2.6 | Bump `versionCode` | `app.json` → `android.versionCode: 17` |

> Note on 2.4: verify nothing still depends on the legacy permissions before
> removing them. `react-native-document-scanner-plugin`, `expo-media-library`
> save paths, and `RNFS` calls outside the app-specific dir are the candidates
> to check.

### 5.3 Build and verify

```bash
npm run prebuild:android
cd android && ./gradlew assembleRelease
# or: npm run eas:build:android:prod

aapt2 dump xmltree app-release.apk --file AndroidManifest.xml | grep -i allowBackup
# expect: android:allowBackup=(0x12000000) false
```

Functional check: install, sign in, send/receive a message, uninstall,
reinstall from Play/backup restore flow. The SQLite cache and AsyncStorage
must come back **empty**.

### 5.4 Rollback

Remove the plugin from `app.json` and rebuild. No persistent state is changed
by this phase, so rollback is total.

## 6. Phase 3 — Media storage boundary (the main event)

**Findings addressed:** F-1 (media survives uninstall), F-2 client half
(backups written to surviving external storage, containing identity keys),
F-7 (E2EE thumbnails written in clear to external storage), F-8 (key loss
writes ciphertext into the gallery).
**Blocked on:** decisions **D1** and **D2**.
**Risk:** medium — this moves the user's photo library. Get D2 right.

### 6.1 The change in one sentence

Stop treating `/Android/media/com.vaultchat.app/**` as the app's media store;
make the private sandbox authoritative, and reduce the external folder to an
explicit, user-initiated export destination (or remove it entirely, per D1).

### 6.2 Work items

| # | Item | Module | Notes |
|---|------|--------|-------|
| 3.1 | Introduce a single storage-roots authority | new module under `lib/` | One list of every root the app writes to, consumed by the media store, GC, storage manager, logout wipe, account switch and panic wipe. This is the structural fix that makes F-6 solvable |
| 3.2 | Repoint the media base path | `lib/mediaStore.ts:31` | Sandbox-private root instead of `ExternalStorageDirectoryPath/Android/media/...` |
| 3.3 | Repoint thumbnails | `lib/mediaStore.ts:88` (`THUMB_DIR`) | Into the sandbox, and encrypt under the per-attachment key when one exists |
| 3.4 | Guard `saveThumb` on key presence | `lib/sendMedia.ts:131,163` | `storeSentCopy` already early-returns when a media key exists; `saveThumb` must do the same. This is a two-line inconsistency causing F-7 |
| 3.5 | Repoint local backups | `lib/cloudBackup.ts:174` | `.vcbak` files into the sandbox |
| 3.6 | Remove identity + ratchet material from the backup bundle | `lib/cloudBackup.ts:72` (`exportE2EEKeys`) | **D5.** A key-escrowed backup that contains long-term identity keys retroactively defeats E2EE for every past and future message |
| 3.7 | Stop `RNFS.scanFile()` on app media | `lib/mediaStore.ts:139,178`, `lib/cloudBackup.ts:193` | Publishing chat media into the system gallery index is a separate consent decision from receiving it |
| 3.8 | Make encryption state explicit on render | `lib/mediaStore.ts:143` (`getMedia`) | Read `meta.encrypted` instead of inferring "no key ⇒ plaintext"; when encrypted-and-keyless, show a clear "cannot decrypt on this device" state and never write ciphertext to a media path (F-8) |
| 3.9 | One-time migration of existing on-disk media | new startup task | See §6.3 |
| 3.10 | Explicit "Save to gallery" / "Export" affordance | `app/media-viewer.tsx` and friends | `MediaLibrary.saveToLibraryAsync` stays — it is consented and correct. It becomes the *only* route to durable, uninstall-surviving storage |
| 3.11 | First-run disclosure | onboarding | State plainly what is stored on the device and what uninstall removes |
| 3.12 | Bump `versionCode` | `app.json` | |

### 6.3 The migration task (this is where the risk lives)

On first launch of the fixed build, per **D2 = migrate-then-delete**:

1. Enumerate the legacy tree `/Android/media/com.vaultchat.app/VaultChat/**`.
2. Move each media file into the new sandbox root, preserving the
   `attachmentId`-derived filename so `pathFor()` resolves unchanged and no
   re-download is triggered.
3. Move `.Thumbs` contents.
4. Move `.vcbak` files, then **re-write them without identity keys** (3.6) or
   delete them if the user opts out of local backups.
5. Delete the now-empty legacy tree, including the directory itself.
6. Record completion in a persisted flag so the sweep runs once, and make each
   step individually resumable — a kill mid-migration must not lose files.

Guardrails:
- **Copy-then-verify-then-delete**, never move-and-hope. Verify size (and
  ideally a hash) at the destination before unlinking the source.
- Free-space check up front; a device with less headroom than the legacy tree
  must migrate incrementally rather than fail halfway.
- Run off the first-frame path (the existing `InteractionManager.runAfterInteractions`
  deferral in `app/_layout.tsx` is the right place).
- Surface progress if the tree is large — this can be gigabytes.
- Log counts to Sentry so field adoption is measurable.

### 6.4 Verification (the acceptance test)

The whole plan exists to make this test pass:

1. Fresh device, fresh install of the **fixed** APK. Sign in.
2. Send and receive: a photo, a video, a voice note, a document, in **both** a
   direct chat and a group chat.
3. Save one photo to the gallery explicitly.
4. Confirm `/sdcard/Android/media/com.vaultchat.app/` is **absent or empty**.
5. Uninstall. Confirm via `adb shell ls` that the path is gone.
6. Reinstall. **Do not sign in.** Expected: no chats, no media, no thumbnails,
   nothing.
7. Sign in. Expected: messages return from the server **only** within the
   retention window configured in Phase 1; media returns **only** if the server
   still holds the bytes (`MEDIA_TTL_DAYS=14`, delivered-purge active);
   older media shows a clean "no longer available" state, not a broken image.
8. The photo saved in step 3 is still in the system gallery — correct, that was
   an explicit user export.

Also verify the **upgrade** path, which is the one users will actually hit:
install the old build, generate media, upgrade in place to the fixed build,
confirm migration moved everything and the legacy tree is gone, and that no
media had to be re-downloaded.

### 6.5 Rollback

Rollback is **not clean once the migration has run** — files have moved. The
mitigations are: ship to an internal/preview channel first (`eas.json` already
defines a `preview` profile with `distribution: internal`), keep the migration
resumable and idempotent, and hold the production rollout until the preview
cohort confirms the upgrade path. Treat the migration commit as one-way.

## 7. Phase 4 — At-rest encryption flags

**Findings addressed:** F-4 (plaintext local message cache), F-10 (plaintext
server-response cache in AsyncStorage).

The sealing layer already exists and is self-tested; it ships **dark**:

```
constants/flags.ts
  VAULT_CACHE_ENCRYPTED = false     ← F-4
  VAULT_SESSION_SEALED  = false     ← paired dependency
```

### 7.1 Work items

| # | Item | Where |
|---|------|-------|
| 4.1 | Complete the two-device verification the flag comments demand | `lib/cacheCrypto.ts`, `services/security/sessionSeal.ts` |
| 4.2 | Enable both flags together | `constants/flags.ts` |
| 4.3 | Evaluate whole-database encryption instead of per-column sealing | `lib/localDb.ts` | Per-column sealing leaves WAL, journals, temp files and the FTS blind index outside the sealed boundary. op-sqlite supports an encrypted build; that is the stronger boundary |
| 4.4 | Route `lib/localCache.ts` through the same sealing layer | `lib/localCache.ts` | F-10 — `vc_cache_*` currently stores raw API JSON |
| 4.5 | Gate cached-data rendering on unlock | `lib/localCache.ts` consumers | Cached content is currently painted on mount, before the app-lock check |
| 4.6 | Key-rotation and unseal-failure paths | `lib/cacheCrypto.ts` | Already designed to fail soft (rows degrade to ciphertext, never crash) — verify under a PIN change and a restored-but-keyless install |

### 7.2 Why after Phase 5

Enabling sealing before the wipe paths are unified (Phase 5) leaves sealed rows
that the account-switch path does not clear, and a stale DEK envelope that
`clearLocalDb()` only partially handles. Ship Phase 5 first.

### 7.3 Verification

- Two-device round trip: set PIN → send → reload → unlock → messages readable.
- With the app locked, a raw read of `vaultchat.db` shows `enc:v1:` prefixed
  values in `messages.content` / `messages.meta` / `chats.data`.
- Duress/decoy PIN cannot read real cached content.
- Search still works: the FTS blind index rebuilds when the keycheck mismatches
  (`ensureFtsReady` already handles this).

## 9. Phase 6 — Per-contact profile-photo keys (deferred)

**Finding:** F-9. `users.photo_key_cipher` wraps the avatar key with the
**server master key** so peers with no E2EE session can still see avatars
(`migrations/043_profile_photo_key.sql`). This is a documented, deliberate
trade-off — not a defect.

Longer term, wrap avatar keys per-contact over the existing pairwise Double
Ratchet, exactly as `STORY_E2EE` already does for stories
(`lib/storyKeys.ts`). Until then, ensure no user-facing copy claims profile
photos are end-to-end encrypted.

## 11. Risk register

| Risk | Phase | Likelihood | Impact | Mitigation |
|------|-------|-----------|--------|------------|
| Retention purge destroys history users wanted | 1 | Medium | High | Staged rollout per §4.1; long max-age first; announce in-app before enabling |
| Manifest change lost by `expo prebuild --clean` | 2 | **High if hand-edited** | High | Config plugin only; verify with `aapt2 dump` on the built APK, not on source |
| Media migration loses files | 3 | Low | **Severe** | Copy-verify-delete; resumable; free-space precheck; preview channel first |
| Migration OOM / ANR on large libraries | 3 | Medium | Medium | Incremental batches off the first-frame path; existing `runAfterInteractions` deferral |

## 13. Closing note

The cryptographic engineering in this codebase is strong — X3DH, Double
Ratchet, sender keys, per-viewer story wrapping, blind-token search, duress
vaults, all with passing self-tests. Every finding in the audit is a
**storage-boundary** problem, not a crypto problem: bytes leaving the sandbox,
keys held by the server, and hardening that shipped behind flags that were
never switched on.

That is the good kind of problem, because none of it requires redesigning the
protocol. It requires deciding where files are allowed to live, and who is
permitted to hold the keys.
