# Tasks

Phases S0–S3 are the spine and ship in order: without the role catalog and the
visibility edge, every later phase leaks data. S4–S5 are additive once S3 lands.

`ponytail:` this plan deliberately builds one engine three ways rather than
three vertical products. If a phase below starts growing a `school_` prefix,
that is the signal it has been designed wrong.

The roster was not in the plan and is unavoidable — a six-year-old has no account, so a users-keyed edge table cannot express the school at all. ## S2 — Run engine
- [x] 2.1 Migration `086`: `runs`, `run_stops`, `run_riders`, `run_events`, plus `chat_members.duty_state` and `space_roster.handover_code`; rider-state CHECK; partial unique index for one active run per driver
- [x] 2.2 `GET/POST /runs`, `GET/PATCH /runs/{id}`, `PUT /stops`, `PUT /riders`, `POST /riders/{id}/state`, `GET /events`, `PATCH /duty`. The lifecycle is a **trigger**, not a handler check, and it stamps `started_at`/`completed_at` itself — a client-supplied "when the bus left" is a client-supplied fact about evidence
- [x] 2.3 Transitions append to `run_events` first, gated by a unique index on `(run_id, transition_id)`. On a retry the insert affects nothing and the state update is skipped — so the row does not get rewritten with a later timestamp and a second actor
- [x] 2.4 Two different permissions, deliberately: a driver starts and completes their own run (`drive_run`), only ops reassigns it (`manage_runs`). Collapsing them would let a driver hand their route to a colleague mid-morning. Rider reads scoped by the 085 rule, per rider, in the RLS policy
- [x] 2.5 **Decided:** riders are `space_roster` rows with an optional `user_id`, not users. Forced by S1 — a six-year-old has no account. Staff and parents carry the link; children do not
- [x] 2.6 `app/space-run-driver.tsx` — one stop, the people at it, two buttons. Tall rows because it is tapped one-handed at a kerb. Optimistic state with rollback (a driver cannot wait for a round trip before turning to the next child) and a `transitionId` on every write, so a double-tap and a retry collapse into one server-side transition. Heartbeat runs only while the screen is open. Nothing space-wide is fetched — and could not be, since the server scopes a driver to their own runs
  - `ponytail:` the Call guardian button says the roster has no phone numbers yet rather than pretending to dial. Wire it when the roster carries contacts
- [x] 2.7 `app/space-run.tsx` — the child's status is the first thing on the screen, because that is the only question a parent opened it to ask. Renders exactly the riders the server returned; there is no client-side filter and must never be one, since filtering here would mean the other children's rows had already been sent to the device
- [x] 2.8 `run_update` / `run_end` / `run_subscribe` relay in the Go socket server + `lib/spaces/runSession.ts`. Three decisions that differ from the plan, each for a reason:
  - **A run gets its own room, not the chat room.** The plan said "the relay's existing membership check", but membership is the wrong gate: a guardian may follow the bus their child is on and no other, and fanning a run out to `chat:<id>` hands every parent in a school every bus. Entitlement is checked once at SUBSCRIBE via `vc_run_visible` — the same function the REST policies call — and room membership then IS the permission, so there is no per-ping database call
  - **No new key and no new message.** A run ping is sealed with the driver's EXISTING presence live-location key. Minting a per-run key means announcing it in the thread; for twenty buses twice a day that is forty system messages nobody reads. Reusing it also makes the audience automatically correct, and means a driver who is not sharing location cannot broadcast a position at all — the right answer, not a limitation
  - **The run channel carries a position, unlike the trip channel.** `tripSession.ts` deliberately publishes only derived values so a trip cannot bypass a member's privacy setting. A run is the opposite case on purpose: the thing shared is a VEHICLE's position, starting the run is an explicit act of going on duty, and it stops when the run does
  - Publishing is gated server-side on being the run's **assigned driver of a started run** — ops may watch every run and still cannot publish a position for one. Delivery, not cryptography, is the confidentiality boundary here, and the code says so rather than implying otherwise
- [x] 2.9 `app/space-ops-map.tsx` — every active run on the existing clustered Leaflet WebView, one socket subscription per run, plus a list showing manifest progress and the server's own staleness verdict. Three states are kept distinct because conflating them is how a map lies: **not reporting** (the server has heard nothing — the one signal that does not depend on this device having listened), **awaiting fix** (it is reporting, this screen has not received one yet), and **a real position**. A vehicle that has not pinged since the screen opened has no dot, and a banner says so rather than leaving a blank map that reads as "nowhere"
- [x] 2.10 `arrivalWindow()` in `lib/spaces/runs.ts`, now fed a **real** distance — haversine from the vehicle's live position to the rider's own stop, divided by its reported speed. A reported standstill is not taken literally (a bus at a red light would otherwise produce an infinite ETA, and "arriving never" is worse than a rough guess). Falls back to the per-stop constant only until the first fix arrives. `ponytail:` still not the Valhalla road estimate — the window's width absorbs more error than the difference — a range, never a point, widening with intervening stops and their dwell variance, sub-linearly (a 16-stop route is not 16× as uncertain as a 1-stop one). Clamps a negative router estimate and never starts in the past. `isDelayed()` is thresholded so a 90-second run is a run, not an incident. **Deviation:** it is fed a crude seconds-per-stop constant, not the Valhalla estimate — that needs the live position stream from 2.8, and is marked `ponytail:` at the constant
- [x] 2.11 `PATCH /duty` (your OWN state only — a dispatcher marking a driver "on duty" from the office is an assertion about someone else's day) and driver reassignment, which logs a `driver_changed` run event and fans out on the socket
- [x] 2.12 Handover verification: `runs.require_code` off by default, code on the roster entry (it belongs to the child, not to one journey), checked server-side on the boarded/dropped transition
- [x] 2.13 `GET /runs/{id}/events` plus `foldReplay()` and the screen's timeline. The road-path absence is **stated** — "this device did not receive the vehicle's encrypted position updates during the run, and the server keeps no copy" — rather than shown as an empty map. `foldReplay` resolves names through a caller-supplied lookup, so a rider the viewer may not see reads as "Someone" and a raw uuid can never reach the timeline
- [x] 2.14 `migrations/tests/086_runs_test.sql` — lifecycle ordering in both directions, timestamp stamping, one-active-run under a real unique index, retry producing exactly one event, invalid state refused, and the parent/driver scope split with direct-by-id reads attempted as a non-superuser
- [x] 2.15 **Applied and rehearsed on production's schema.** All of `086_runs_test.sql` passes: lifecycle refused in both wrong directions, timestamps stamped by the trigger, the second concurrent start rejected by the unique index, a retry producing exactly one event, an invalid rider state refused, and the parent/driver scope split verified with direct-by-id reads as a non-superuser. RLS enabled + forced on all four tables

## S3 — Dashboards
- [x] 3.1 `tilesForType()` picks the board from the space's TYPE, because the QUESTION differs rather than the styling: a school counts children (expected / travelled / still on a bus / unaccounted), a cab fleet counts vehicles, and a space with no runs gets no operations board at all rather than a row of zeros. Entry to the surfaces is still gated on the ops PERMISSION, which is the right test for who sees them — the type decides what they are looking at, the permission decides whether they may
- [x] 3.2 `lib/spaces/dashboard.ts` — `opsTotals`, `rollCall`, `transportTiles`, `attendanceTiles`, all derived, nothing stored. What the self-check pins:
  - **A stale SCHEDULED run is not "not reporting"** — it has not started. Flagging tomorrow morning's bus offline all night is how an alert becomes wallpaper
  - **`unaccounted` is its own figure**: riders left pending on a run that has FINISHED. Nobody marked them either way, so the record cannot say whether they travelled — and that is not the same as absent and is never added to it. This is the number a naive dashboard omits and the only one on a school board that means "go and check"
  - **Alert colour is reserved for what is actually wrong.** Riders still to collect on a running route is the normal state of a bus halfway round; a healthy board has no alerts at all, asserted directly
  - **Recomputation is total** — same input, same numbers, asserted, because a count that is kept and a count that is derived can disagree and it is always the dashboard that gets believed
- [x] 3.3 `app/space-roster.tsx` — **one screen for every viewer**, because the server decides what is in it: a parent gets their own child, a supervisor their reporting line, ops the space. No role switch and no client-side filter; a filter here would mean the rest of the roster had already been sent to the device. The `truncated` flag is rendered, not logged — a supervisor silently missing half their line is worse than one told the hierarchy is deeper than the walk. The fleet view is the operations map, and the supervisor's attendance view is 4.5; between them 3.3 is served without a per-role screen each
- [x] 3.4 A driver whose run is STARTED is routed to their manifest on opening the space. Three guards, each because the alternative traps someone: only while a run is actually out (an off-duty driver keeps the whole app instead of being bounced out of it every launch); only for a driver who is not also ops (a Transport Manager who drives needs the dashboard they came for); and ONCE per mount, so pressing Back returns to the dashboard and stays there rather than bouncing straight out again
- [x] 3.5 `npx tsx lib/spaces/dashboard.ts` — empty board is complete rather than stalled, status counts, the stale-scheduled case, roll-call separation of unaccounted from not-travelling, cancelled riders never counted as expected, alert discipline in both directions, and pure recomputation asserted by comparing two runs over the same input

## S4 — Attendance
- [x] 4.1 Shift window config per space: `chats.shift_start/shift_end/shift_grace_minutes` (087) + `PATCH /chats/{id}/shift`. `TIME`, not `TIMESTAMPTZ` — a shift is "09:00 local, every day", not an instant. These three columns are the ENTIRE server-side footprint of attendance
- [x] 4.2 `lib/spaces/attendance.ts` — a pure projection over the `enter`/`leave` crossings the geofence already records. No attendance engine, no attendance table. **Unknown is never folded into absent**, and `summarise()` reports it as its own figure: a dashboard reading "3 absent" when the truth is "1 absent, 2 phones off" is the failure the whole module is arranged around. Also refuses to judge a day before it is over — nobody is absent at 08:30 for a 09:00 shift — and counts lateness past the GRACE period, not past the start
- [x] 4.3 Falls out of 4.2 by construction: no crossings means no state, which is `unknown`, which is displayed as "No data" rather than counted against anyone
- [x] 4.4 Migration `087`: `visitor_passes` + issue/redeem/exit endpoints. Single-use is a **conditional UPDATE**, not read-then-write: two gates scanning one code in the same second is exactly what check-then-set loses. Code minted with `crypto/rand` (it opens a door) from an alphabet without I/O/0/1 (it gets read aloud). Expired, used and never-existed all return one message, so the endpoint is not a code oracle
- [x] 4.5 `app/space-attendance.tsx` — today's states, a 7-day strip per person, and a weekly roll-up. Computed on the device, uploaded nowhere, and reachable only on the ops permission (attendance is meaningful where someone oversees others, not in every household).
  - **A gap this phase exposed and closed:** `processFix` evaluates geofences only for a device's OWN fixes, so `enter`/`leave` alerts live on the phone that crossed the zone and nowhere else — a supervisor had no crossings for their team at all. Attendance for other people is therefore derived from the position SAMPLES this device already holds, via `crossingsFromSamples`. No new event, no new sync, nothing uploaded
  - The derivation mirrors `evaluateFences`: leaving needs to clear the radius by a margin, so a phone jittering on the boundary does not manufacture a dozen arrivals. Entering has no margin — being early to work should not have to be proven twice
  - **A first sample outside the zone is a starting position, not a departure.** Recording a `leave` there would invent an exit from a place nobody was seen to enter
  - The screen states its own limits rather than implying completeness: it reflects only the updates this device received, "No data" is grey and never red, and the footer says outright that it is a view and not a payroll record
- [x] 4.6 `npx tsx lib/spaces/attendance.ts` — clock parsing including everything that must NOT parse, grace-period edges, late-by measured from grace, left-early only when they actually left before the end, open-ended stays counted to now, an unmatched `leave` yielding zero rather than negative time, out-of-order input folded correctly, and unknown-vs-absent asserted directly. Pass single-use and expiry are covered by `migrations/tests/087_space_ops_test.sql`

## S5 — Ops comms
- [x] 5.1 **No column.** The audience rides in the message's existing `meta` JSONB beside `meta.announcement`, which the server already reads. A column would duplicate a field the message spine already carries
- [x] 5.2 `chatsAudienceAllowed` validates the audience in the message POST path, next to the send-permission check — so a client that skipped the composer cannot attach an audience its sender may not address. **Honest limit, now written into the spec:** an audience scopes notification and display, NOT readability. The ciphertext still reaches every member of the chat, because that is what being in a chat means
- [x] 5.3 Migration `087`: `space_incidents` + list/file/resolve endpoints. Photos go through the existing space album by reference; the note is ciphertext and only the CATEGORY is plaintext, which is what lets ops triage without reading it. Only ops may close one — a driver who could resolve their own breakdown report could also make it disappear
- [x] 5.4 `lib/spaces/detect.ts`, fed from the driver screen's own position watcher. Two new alert kinds (`overspeed`, `longstop`) added to the shared alert model at `important` severity. What the self-check pins:
  - **Every condition is sustained and hysteretic.** A detector that fires on every fix while a condition holds produces forty alerts for one incident, and forty alerts is the same as none. Overspeed must persist 15s to raise and must drop below 90% of the limit to re-arm, so a vehicle sitting exactly on the threshold cannot flap
  - **Implausible fixes are discarded, not believed.** A fix claiming worse than 100 m accuracy is ignored entirely, and a derived speed above 60 m/s is dropped — a phone re-acquiring GPS after a tunnel jumps 3 km in 10 s and would otherwise alert a whole school at 400 km/h
  - **Deviation is measured against the stop sequence, point-wise and coarse.** Pretending to segment precision over points kilometres apart produces confident nonsense; the 250 m threshold is set for what the data actually is. No stops means no deviation claim, never "off route" against nothing
  - **Two conditions can fire at once** — a vehicle can be off-route AND stationary, and reporting only the first hides a breakdown behind a wrong turn
  - **The alert text never carries a coordinate**, asserted by the self-check. Same rule `tripSession.ts` follows: report the fact, never the position
- [x] 5.5 Stale-stream detection: `runs.last_ping_at` + `POST /runs/{id}/ping` (proof of life, carrying NO position) and a **derived** `stale` flag in the run payload. Derived, not stored: a stored flag needs a sweep to keep it true, and a sweep that falls over leaves every bus looking healthy — the exact failure the flag exists to catch. `ponytail:` push escalation for staleness still needs a background sweep; the read-path flag covers the dashboards
- [x] 5.6 Driver panic control on the run screen — deliberately NOT one of the incident categories, because an incident is a form you fill in and a driver in trouble is not filling in a form. One confirmation to survive a pocket press, then a local `sos` alert (critical, and not dependent on the network) plus an incident record so it lands in the queue ops already watches. Escalation lands via `opsNotifyStaff` (5.8), and since migration **088** an SOS is its own incident category with its own wording ("EMERGENCY · Bus 01") and its own Android notification channel — so it can carry a distinct sound and is not silenced along with routine incidents. A category rather than a separate table: an SOS *is* an incident (reporter, run, status, resolution), and a parallel table would need its own policies, endpoints and list screen to say the same things. **The Android channel had to be created client-side too** — the server addresses `channelId: "sos"`, and a channel id Android has never been told about falls back to default SILENTLY, so the distinct wording would have arrived with the same sound as a blocked road. It is MAX importance and bypasses Do Not Disturb, like calls; ordinary incidents deliberately do not get that, because a channel that cries wolf gets muted and takes the real emergencies with it
- [x] 5.7 The instruction composer lives on the operations map — all active runs, their state, and a targeted send from the same screen, which is what "without leaving the view" asks for. Addressed as `run:<id>` through the announcement path, so the server re-checks the audience and the composer cannot address what its sender may not. Emergency mode is now a MODE rather than a label, because it changes what the composer does: it addresses every run on the road at once instead of the one selected on the map, which is the action an office actually needs during an incident. Still one addressed announcement per run, so a parent whose child is not out is not woken about vehicles they have nothing to do with; a partial failure reports HOW MANY reached, since "partly sent" with no number is what makes an operator resend to everyone. Deliberately session-local and never persisted: a stored "we are in an emergency" flag is one nobody remembers to clear
- [x] 5.8 `runNotifyGuardians` (rider transitions) and `opsNotifyStaff` (incidents), both off the request path via `workx.Submit` — a driver at a kerb waits for the database write, never for Expo.
  - **The recipient set is the REVERSE visibility walk**, from the rider back up the links to their guardians and anyone supervising those guardians, depth-bounded exactly like `space_visible_roster`. That is what makes "a notification never names an unlinked rider" true: there is no broadcast being filtered, so an empty audience means nobody is told rather than everybody
  - **The split between the two channels is the point.** The socket event stays content-free because it fans out to a ROOM, and a room is the wrong granularity for a child's name. The push is addressed per user, so it can and does say who it is about
  - An **archived** guardian stops being notified immediately, not at the next deploy — asserted in the test
  - `opsNotifyStaff` names the category and the vehicle, never the note: the note is ciphertext this server cannot read, and a push is not the place to start trying
- [x] 5.9 `migrations/tests/087_space_ops_test.sql` extended with the recipient walk: exactly one recipient for a linked rider and it is the right one, **zero** for an unlinked rider, and zero once the guardian is archived. All four blocks pass against a copy of production's schema
- [x] 5.9 `migrations/tests/087_space_ops_test.sql` — pass single-use under a same-second second attempt, expiry, inverted window, incident visibility for the on-run parent / unrelated member / reporter / ops, filing-as-someone-else refused, and staleness including "a scheduled run is not stale" (reporting tomorrow's bus offline all night is how an alert becomes wallpaper)

## Bug found while checking family invitations (2026-08-11)

Reported as "family invitation is not working properly". Diagnosed from
production data rather than from the description, and it was real.

**Symptom.** An invited person is never added, and the inviter watches them
never arrive. Production had exactly one such row: invitation 2, status
`accepted`, `responded_at` NULL, invitee not a member — stranded since
2026-08-06 while every other invitation reached `joined`.

**Cause — three correct pieces that did not join up.** An invitation can strand
at `accepted` when a group was on the old `strict` default and the owner
approval it waits for was never surfaced (the migration 077 fallout). Both the
recovery paths for that already existed: `membershipAccept` explicitly re-opens
a stranded row, and `/invitations` sets `canAccept` on exactly those rows so the
inbox draws an Accept button.

What did not join up was **discovery**. The invitations banner on the chats tab
counted `status === 'pending'` only — so a stranded invitation was not counted,
the banner stayed hidden, and for anyone not already in a space that banner is
the ONLY route to the inbox. The recovery existed on the server and on the
screen, and could not be reached from either end.

**Fix.**
- The banner now counts what the invitee can ACT on — the server's own
  `canAccept` — rather than what is literally pending, with a status fallback so
  it stays right against an older server. Verified against the real row: counted
  `false` before, `true` after
- The inbox told a stranded invitee "waiting on an admin to approve you" while
  showing the button that would have finished the job. It now says "You accepted

  is shown only for a genuine wait — never beside the control that ends it

**Not a regression from this change.** The stranded row predates it, and nothing
in Spaces & Operations touches the invitation path.
